先说实在话：2026-09-22 那天，我走到 a3 跟前——那台 i9-14900K 塔式机，是我*唯一*的 Kubernetes 控制平面——它摸上去发烫、往外吹热风，SSH 也不应答。从早上 9:15 起它就一直这样了。九个小时。我最初的猜测都是家庭实验室的老熟人：风扇坏了、积灰、某个 GPU 任务失控。全都不是。两个 CPU 核心整段时间都在*Linux 内核内部*的死循环里以满睿频空转，这就是一台硅做的暖风机的样子。内核九个小时前就知道了。只是没人告诉过它该怎么办。

## 我终于去看时发现了什么

a3 被我硬关机前，日志的最后一行是这个：

```
watchdog: BUG: soft lockup - CPU#12 stuck for 30629s! [kubectl]
```

三万秒。内核自己的看门狗从 09:15 起就一直在打印这条抱怨，数字越来越大。牵涉两个核心：一个在跑一个正在处理缺页的 `kubectl` 进程，另一个在跑一个 root 权限的 `fuser`，它正在读取每个进程的 `/proc/PID/maps`。两者卡在同一个地方——内核用来查找某个地址属于哪段内存映射的枫树（maple tree）遍历——而且谁都永远出不来。

单个核心卡住很糟，但还能活。让它变成一次完整故障的是：那条卡死的路径握着 `rtnl_lock`，也就是守护内核网络配置的那把锁。两分钟之内，`NetworkManager`、`k3s-server`、甚至 `node_exporter` 都被报告为在等这把锁的挂起任务。网络栈卡死，SSH 随之而去，k3s server 在接下来的九个小时里每秒记一条"network policy controller heartbeat missed"。因为 a3 是唯一的控制平面，集群 API 整段时间都处于降级状态。另外五个节点上的 Pod 一直在跑——Kubernetes 承诺的这部分兑现了——但什么都不能调度、变更或修复。

**已排除**，留个记录：GPU（空闲，重启后 31 °C）、内存（52 GB 空闲）、磁盘（SMART 干净），以及行为异常的 Pod（空转的线程在内核侧，不在用户态）。过热降频是*结果*，不是原因。

## 为什么持续了九个小时

这才是我真正想记下来的部分，因为内核 bug 算不上我的错，而这九个小时大部分是。

**a3 跑的是一个从不更新的内核。** 它运行的是 6.17.0-14，一个"裸"内核包，没有元包（meta-package）来拉取小版本更新。这种事通常发生在某次别的紧急情况里手动装了个内核，然后没人回头收拾。这里陷入循环的 `/proc/PID/maps` 代码路径在后续内核里已经被重写。与此同时，a1——同一档硬件、同样的负载风格——早已悄悄在 7.0 HWE 线上跑了好几周，零锁死。我手里有个对照组，自己却不知道。

**没有任何东西被配置成锁死后重启。** Linux 出厂默认 `kernel.softlockup_panic=0`，意思是"记一笔，继续跑"。硬件看门狗也没加载。对一台有人能走过去的服务器来说，这个默认值说得过去。对一台放在储物间里的无头机器，它把一次两分钟的重启变成了九小时的暖风机。

**没有一条告警覆盖"活着但卡住"。** 我的[告警](/observability/alerting)里有一条 `NodeDown`，是用血泪换来的，而它没有触发——因为 a3 从来没有完全消失。node-exporter 还活着、还在被抓取，只是从一台网络栈卡死的机器上慢吞吞地回话。两个核心 100% 处于*内核态*，这是一个响亮、不会认错的信号，而我没有一条规则在听。

**CPU 跑着 2023 年的微码。** 不是触发因素，却是事后最让我后怕的一点。`intel-microcode` 包不知何时被卸掉了，于是 14900K 一直靠 BIOS 微码 `0x11d` 启动——那是 Intel 修复 Raptor Lake 不稳定问题之前的版本，而这颗 CPU 正是因为那个问题出名的。内核每次启动都在给自己打 `CPU_OUT_OF_SPEC` 的污点标记。它就在日志里。我从来没看过。

## 修复：三层，一个脚本

所有东西落在一个脚本里，[`scripts/node-lockup-guard.sh`](https://github.com/briancaffey/home-lab/blob/main/scripts/node-lockup-guard.sh)，它现在和 [T430 那篇](/hardware/nodes#t430--the-second-laptop-node)里的屏蔽睡眠、关闭 WiFi 省电一起，成为节点必做的准备工作。当晚它就在 a1、a2、a3 和 t430 上跑了一遍。

1. **锁死即 panic，panic 即重启。** 内核的软锁死和硬锁死检测器切换到 panic 模式，阈值 30 秒，panic 超时设为 15 秒。一个卡在内核里的核心现在会让机器在大约 75 秒内关机再开机。听起来很粗暴，确实也是——但一次计划外重启恰恰是 Kubernetes 为之而生的故障模式。Pod 重新调度；节点回到 `Ready`；我收到一条 `NodeRebooted` 告警和一份可以读的日志。
2. **软件看门狗后面再放一个硬件看门狗。** Intel 芯片组里有一个 TCO 看门狗，没人喂它就会复位主板。它由一个小小的 systemd 单元在启动时加载，再由 systemd 自己喂狗（`RuntimeWatchdogSec`），这样即使 PID 1 都停了，芯片组也会拔掉插头。一个值得知道的细节：Ubuntu 的内核包把看门狗驱动列入了拒绝加载名单，所以常规的 `modules-load.d` 方式会静悄悄地什么都不做——因此才需要专门的启动单元。
3. **微码由操作系统在每次启动时加载。** `intel-microcode` 重新装回并验证。a3 现在以 `0x133` 启动，也就是这颗 CPU 当前的稳定性版本，由内核的早期加载器加载，不管 BIOS 带的是什么。

再加一个参数，脚本会安装 HWE 内核*元包*，这才是"从不更新"的真正解法：a3 从 6.17.0-14 升到了 7.0.0-34，NVIDIA 的 DKMS 模块干净地重新编译，旧内核留在 GRUB 里作为后备。

集群这边，新的 `node-runaway` 规则组给了 Prometheus 之前缺失的词汇：`NodeCPUStuckInKernel`（critical——任意 CPU 内核态占比超过 95% 持续十分钟；光这一条就会在 09:25 把我叫起来）、`NodeHighTemperature`、`NodeIOStalled` 和 `NodeRebooted`。四条都在[告警页](/observability/alerting)上。

## 我没料到会发现的事

事后分析总会翻出东西。看着 a3 重新起来，它在大约 50% 的 I/O 压力停滞里待了一刻钟，等每个 Pod 重启，探针左一个右一个地超时。原因：a3 的 k3s 数据目录——containerd 的镜像存储、每个容器的可写层，以及大约 14 GB 的节点本地数据库卷——放在一块 5400 转的机械硬盘上。SQLite 数据存储早就从 SSD 绑定挂载过来了，所以我一直以为其余部分也是。并不是。这不是机器过热的原因，却是"a3 重启后总感觉抖"这几个月来一直存在的背景噪音的原因。把这些数据挪到 SSD 是清单上的下一项，再加上给 Z790 主板更新 BIOS。

## 我从中带走的

- **卡住的节点必须能自己重启。** Linux 的默认行为——记一条锁死日志然后继续空转——对任何你无法在几分钟内走到跟前的机器来说都是错的。`softlockup_panic=1` 加一个硬件看门狗是便宜的保险，我第一天就该有。
- **"宕机"和"卡住"是两条不同的告警。** 我有前者，并假定它覆盖了后者。它不覆盖。一台从卡死内核里慢慢回话的节点，在存活规则眼里是*活着*的。
- **看看你到底在跑哪个内核，以及有没有东西在更新它。** `uname -r` 加 `apt list --installed 'linux-generic*'` 是十秒钟的审计。a1 当了我几周的对照组，我从没比较过。
- **读一读污点标记。** 14900K 上的 `CPU_OUT_OF_SPEC` 不是装饰。
- **单控制平面又一次成了单点故障。** 我抽象地知道这一点；现在我把它知道成了一个数字（九个小时）。[高可用计划](/foundations/k3s#plans-to-migrate-to-ha)仍然以网线布线为前提，这次事件把网线往清单上方推了，而不是把高可用往下拉。

带内核栈的完整事后分析在仓库里的 [`docs/22`](https://github.com/briancaffey/home-lab/blob/main/docs/22-a3-thermal-runaway-postmortem.md)，[六台机器](/hardware/nodes#a3--control-plane)里 a3 那一节是简短版。从那以后 a3 一直安静、凉快，跑着更新的内核和新鲜的微码，而且——头一回——有了一份它出问题时该怎么办的方案。
