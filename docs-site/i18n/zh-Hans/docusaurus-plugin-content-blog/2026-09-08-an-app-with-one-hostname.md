先说实在话：这周我给 [hn.fm](/media/hnfm)——我那个把 Hacker News 做成视频的应用——开了第二扇前门，在 `hnfm.lan` 旁边加了一个 tailnet 主机名，这样我在任何地方都能看当天的渲染结果，而不用开放端口。Kubernetes 这一侧毫不费事：多一个镜像同一张路径表的 Tailscale Ingress，多一块 Homepage"Tailnet"分组里的磁贴。然后页面在新域名上加载出来了，并且什么都不干。这次失败才是有意思的部分，因为每一个原因都在*我的*代码里，而且每一个都是同一个错误换了件衣服。

## 三个症状，一种病

**前端敲错了门。**Nuxt 应用在构建时烤进了一个绝对的 API base——`NUXT_PUBLIC_API_BASE=https://hnfm.lan`。用 tailnet 域名打开的浏览器渲染出了外壳，然后去局域网域名上找 API，而那是它够不到的。对一个相信自己只有一个地址的应用来说，这行为完全正确。

**CORS 也这么认为。**后端只允许一个源：`https://hnfm.lan`。就算前端猜对了 API 主机，tailnet 域名上的浏览器也会被拒。

**媒体 URL 是为错误的主机签的。**这一个我没料到。媒体从 MinIO 桶通过预签名 URL 提供，而预签名 URL 是针对特定 `Host` 签的。为 `hnfm.lan` 签的链接通过 tailnet 域名去取，返回 `SignatureDoesNotMatch`。视频*确实*在那儿；签名只是在说，你从错误的那扇门要它。

三个看起来毫不相干的失败——一个前端环境变量、一张 CORS 名单、一个 S3 签名——一个根因：**应用假定自己只有一个主机名。**

## 每一处修复都在应用里

Ingress 之后集群里什么都没改。全部改动落在 hn.fm 仓库里：

- **空的 API base。**`NUXT_PUBLIC_API_BASE` 现在留空，浏览器在提供页面的那个主机上调用 `/api`。同源，于是 CORS 的问题也整个消失了。
- **一个小小的服务端代理。**服务端渲染没法用相对 URL——那时候还没有页面源。所以一个 Nitro 通配路由把 `/api` 转发到集群内部的 web Service（`http://hnfm-web:8000`）。浏览器和 SSR 走不同的路到达同一个后端，而两者都不需要知道公网主机名。
- **为敲门的那扇门签名。**媒体端点现在为请求*到达时*所用的源构造预签名 URL——`X-Forwarded-Host` 和 `X-Forwarded-Proto`，回退到 `Host`——只要公共媒体 URL 与 API 同主机。从局域网域名来问，就拿到为局域网域名签的链接；从 tailnet 来问，就拿到为 tailnet 签的。

这之后，同一套部署在两个名字上都能正确应答，而 `clusters/home/tailscale/` 里的那个 Tailscale Ingress 文件只是 chart 路径表的忠实镜像，顶上带着一条醒目的注释："那边加了路径，这边也要加。"

## 我要留下的规矩

我给这个实验室写了不少小服务，现在我把"只有一个主机名"当作代码审查时的一种坏味道。要找的三样东西，就是咬了我的那三样：

1. **环境变量里的绝对公网 URL。**如果某个构建期或运行期变量里含有一个*浏览器*会用到的主机名，那就是一个等着发作的第二主机名 bug。优先用相对 URL；从请求中推导源。
2. **单一源的 CORS。**通常是第一个问题的症状。同源设计基本上让它不再必要。
3. **绑定主机的签名。**预签名 S3 URL、签名 cookie，任何把主机放进 HMAC 的东西。为请求来自的那个主机签名，而不是第一天配置的那个。

这些都不新鲜——就是十二要素里"别把环境硬编码"的老生常谈——但我以前只把它当作*部署*卫生来听。这是我第一次把它当作*网络*约束来体会：服务一旦拿到第二个名字，关于第一个名字的每一条隐藏假设都会变成 bug。hn.fm 的大门仍然是 tailnet 的 ACL（它自己没有登录，而 tailnet 默认拒绝），所以安全姿态没有变。只是应用不再相信自己只住在一个地址上——而这本来就是一个跑在集群上的应用从一开始就该相信的事。
