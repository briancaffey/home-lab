Tetragon sees what your containers do after they start.

An eBPF sensor on every node that records process, file and network activity with pod identity attached, filters it in the kernel, and can kill a process mid-syscall. Here is what it is, what it would catch on this cluster, and a three-phase plan that is already written as manifests.

v1.8.0 · 30 Oct 2026 Cilium sub-project · CNCF Apache-2.0 kernel 4.19+ with BTF works on flannel — no Cilium CNI

Verdict: run it, observe-first.

Nothing on the cluster watches runtime behaviour today. Trivy knows what is in an image, Prometheus knows whether a pod is up, Loki knows what it printed. None of them would notice a shell opened inside Vaultwarden. Tetragon closes that gap with one DaemonSet, and its output lands in the Loki, Prometheus and Alertmanager you already run. Detection carries almost no risk; enforcement is powerful enough to hurt, so it comes last and on one namespace.

The gap it fills

What each layer of the current stack can and cannot tell you about a compromised pod.

before deploy

Harbor + Trivy

Known CVEs in images you store and run. Says nothing about what a process does.

health

Prometheus

Up, down, slow, full. A cryptominer shows as "CPU high" at best.

stdout

Loki + Dozzle

Only what the app chose to print. An intruder's shell prints nothing.

runtime

Tetragon

Every exec, plus chosen file, network and privilege events, per pod, from the kernel.

still open · audit M1

Network policy

Tetragon reports and can kill connections, but it is not a firewall. NetworkPolicies remain a separate job. Policy 06 gives you the traffic inventory to write them.

still open · audit M6

Admission control

Pod Security Admission stops a bad pod spec from being created. Tetragon acts after the pod is running. You want both.

How it works

Policy is compiled into eBPF programs. Filtering and enforcement happen inside the kernel; only matching events cross into user space.

Step 3 is the differentiator. Because the decision is made in the kernel, at the hook, a blocked call returns an error before it completes. A user-space tool can only react after the fact.

Base sensor, no policy

Every process start and exit with binary, arguments, parent, uid, pod, namespace and image. Optionally capabilities and Linux namespaces.

TracingPolicy

A CRD (cilium.io/v1alpha1) naming kernel functions to hook, which arguments to read, and selectors for binary, path, address, capability, pod labels or node.

Policy mode

Any enforcing policy can run in monitor mode: it reports what it would have blocked and blocks nothing. This is what makes enforcement safe to learn.

What it would catch here

Six detection policies, each tied to a finding from the June security audit (doc 09). All six only post events. None can break a workload.

With no policy at all, phase 1 already answers: which pods spawn shells, what runs from /tmp, and which processes hold CAP_SYS_ADMIN or sit in the host PID namespace.

What a policy looks like

kind: TracingPolicy
metadata: { name: sa-token-read }
spec:
  podSelector: {}                         # pods only, never the host
  kprobes:
  - call: "security_file_permission"      # 1 · hook: every file read/write check
    args: [{index: 0, type: file}, {index: 1, type: int}]
    selectors:
    - matchArgs:                          # 2 · filter, in the kernel
      - { index: 0, operator: Prefix, values: ["/run/secrets/kubernetes.io/serviceaccount"] }
      - { index: 1, operator: Equal,  values: ["4"] }      # MAY_READ
      matchBinaries:
      - { operator: In, values: ["/bin/busybox", "/usr/bin/cat"] }
      matchActions:
      - { action: Post, rateLimit: "1m" }    # 3 · act — swap for Sigkill to enforce

The rollout

Three phases. Each one is useful on its own, and you can stop after any of them.

week 1
1

Observe

Merge the branch. Argo CD installs the agent on every node; process events flow to Loki through the existing promtail. Learn what normal looks like, watch event volume and agent memory for a week.

Risk: a privileged-ish DaemonSet and some log volume. Nothing is blocked.
weeks 2–3
2

Detect

Uncomment one line to enable the six policies. Trip each on purpose (the runbook has the commands) and watch the alert arrive in Telegram. Tune the noisy ones: apt upgrades will touch systemd units, your own sudo cat will trip the k3s policy.

Risk: alert noise, and a policy that fails to load on a kernel missing a hook. There is an alert for that.
week 4+
3

Enforce — Vaultwarden only

One rule: inside the Vaultwarden pod, only the /vaultwarden binary may touch /data. Anything else gets EPERM and is killed. It ships in monitor mode; flip it to enforce after two weeks in which the only would-have-blocked events are your own tests.

Risk: real. A wrong allowlist kills legitimate processes. Scoped to one pod, with a one-line break-glass.
Sigkill is not a block. A kill signal ends the process but does not guarantee the syscall that triggered it was stopped: the write may already have landed. Override makes the call itself return an error. The Vaultwarden policy uses both, as the Tetragon docs recommend.

Costs and caveats

Kernel hooks are not a stable API

kprobes attach to internal functions that get renamed between kernels; one missing hook fails the whole policy on that node. Your nodes span 6.17, 7.0 and NVIDIA's DGX kernel. Re-check after every kernel bump.

It is a root-equivalent agent

The DaemonSet runs on the host network with SYS_ADMIN, BPF-class capabilities and host mounts. Since 1.8 it is no longer privileged: true, but it joins the list of high-value pods from audit L1.

Overhead is small but not published independently

The docs give no figures. The only numbers are the vendor's from 2023: 1.68% on a kernel build, 2.46% with JSON export. security_file_permission, used by four of these policies, is a hot path; measure on a GPU node before trusting that.

Pod filtering is best-effort without runtime hooks

Tetragon learns about new pods from the API server, so the first instants of a container can escape a pod-scoped policy. Runtime hooks (NRI) close that, and are left off here to keep phase 1 simple.

It does not stop root on the node

Tetragon's own threat model excludes an attacker who is already root on the host. Events can also be dropped under flood. It is a detection layer, not a guarantee.

Event volume is yours to manage

Exec events for every pod add up. The values file drops exit events and host exec noise, and an alert fires past 8 GB per day raw. Each event also carries 6.3 KB of node labels that Tetragon cannot drop; strip them in promtail.

What is already prepared

Phase 1 has been live since 24 Nov 2026: agents on all seven nodes, events in Loki, metrics and alerts in Prometheus. The policies are in the repo but not yet enabled.
